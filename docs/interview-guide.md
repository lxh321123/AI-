# 面试讲解文档

## 项目一句话介绍

这是一个面向企业内部 AI 分析场景的任务调度与结果管理平台，核心是用 Java 后端技术完成任务提交、异步处理、状态流转、结果查询、幂等控制和失败补偿。

## 项目背景

AI 分析任务通常有三个特点：

- 处理耗时不稳定，可能几百毫秒，也可能几秒甚至更久。
- 用户可能重复点击提交，容易产生重复任务。
- 任务执行过程中可能失败，需要记录原因并支持重试。

所以我没有把它做成简单的同步接口，而是设计成异步任务平台：用户提交任务后快速返回 `taskId`，后台消费者异步执行，用户通过查询接口查看状态和结果。

## 核心业务流程

1. 用户调用创建任务接口，传入 `taskName`、`taskType`、`inputText`、`bizId` 和优先级。
2. 系统先做参数校验和幂等检查。
3. 任务写入 MySQL，初始状态为 `PENDING`。
4. 事务提交后投递 RabbitMQ 消息。
5. 消费者收到消息后把任务改为 `PROCESSING`。
6. 调用 Mock AI 服务生成结果。
7. 结果写入 `ai_task_result`，任务改为 `SUCCESS`。
8. 查询任务详情和结果时优先走 Redis 缓存。
9. XXL-Job 定时扫描超时任务和失败任务，做失败补偿。

## 为什么用 MQ

我使用 RabbitMQ 是为了解耦任务提交和任务执行。

如果创建接口直接同步调用 AI 服务，接口耗时会变长，用户体验不好；一旦 AI 服务抖动，也会影响创建接口。用 MQ 后，接口只负责落库和发消息，后台消费者慢慢处理任务，可以削峰、异步化，也更方便做失败重试。

## 为什么用 Redis

Redis 在项目里有四个作用：

- 创建任务时做 `bizId` 幂等锁，防止并发重复提交。
- 缓存 `bizId -> taskId`，重复提交时快速返回已有任务。
- 缓存任务详情和任务结果，减少数据库查询。
- 消费任务时做处理锁，避免同一个任务被多个消费者重复处理。

## 如何做幂等

创建任务的幂等分三层：

第一层是 Redis `biz-task:{bizId}`，如果命中，直接返回已有 `taskId`。

第二层是 Redis `create-lock:{bizId}`，防止同一业务 ID 在并发请求下同时创建。

第三层是 MySQL `biz_id` 唯一索引，作为最终兜底。即使 Redis 锁失效，数据库也不会允许重复写入。

消费端幂等也有三层：

- Redis `process-lock:{taskId}` 防止同一任务并发执行。
- 判断任务是否已经是 `SUCCESS`。
- 结果表 `task_id` 唯一索引防止重复写结果。

## 如何保证任务状态一致性

任务状态只允许按固定方向流转：

```text
PENDING -> PROCESSING -> SUCCESS
PENDING -> PROCESSING -> FAILED
FAILED -> PENDING -> PROCESSING -> SUCCESS
```

创建任务时，任务入库和操作日志在同一个事务内完成。MQ 消息在事务提交后发送，避免数据库回滚但消息已经投递的问题。

消费任务时，先把状态从 `PENDING` 改成 `PROCESSING`，处理成功后写结果并改为 `SUCCESS`，异常时记录失败原因并改为 `FAILED`。状态变化后会删除 Redis 缓存，避免用户读到旧状态。

## 如何处理失败和重试

失败处理分两类：

- 消费过程中出现异常：记录 `failReason`，任务状态改为 `FAILED`，写入任务日志。
- 任务长时间卡在 `PROCESSING`：XXL-Job 定时扫描，超过阈值后标记为 `FAILED`。

重试也分两类：

- 用户手动调用 `/api/tasks/{taskId}/retry`。
- XXL-Job 定时扫描失败任务，未超过最大重试次数则自动重新投递 MQ。

项目里通过 `retry_count` 和 `max_retry_count` 控制重试次数，防止失败任务无限重试。

## 如何设计数据库表

我设计了三张核心表：

- `ai_task`：任务主表，保存任务 ID、业务幂等 ID、任务类型、输入内容、状态、优先级、重试次数和失败原因。
- `ai_task_result`：任务结果表，保存结果文本、摘要、模型名、token 数和耗时，`task_id` 唯一。
- `ai_task_log`：任务日志表，记录创建、开始处理、成功、失败、重试等事件。

这样主流程、结果数据和操作日志相互独立，查询和排查问题都比较清晰。

## 如何设计缓存

缓存采用 Cache Aside 模式：

- 查询任务详情时先查 Redis，没有再查 MySQL，然后写入 Redis。
- 查询成功任务结果时也先查 Redis，没有再查 MySQL。
- 任务状态变化、结果写入、失败重试时删除相关缓存。

这样可以降低数据库压力，同时通过状态变化后主动删除缓存，减少脏数据问题。

## 如何设计定时任务

我实现了两个调度任务：

- `markTimeoutAiTaskJob`：扫描长时间处于 `PROCESSING` 的任务，标记为失败。
- `retryFailedAiTaskJob`：扫描失败但还没超过最大重试次数的任务，重新投递 MQ。

本地为了方便使用 `@Scheduled` 就能运行；如果接入公司环境，可以通过 XXL-Job Admin 统一调度和查看执行日志。

## 可能被追问的问题和回答

### 1. 你怎么保证 MQ 消息和数据库事务一致？

我采用的是“事务提交后投递消息”的方式：任务记录先在事务里落库，事务提交后再发送 RabbitMQ 消息。这样至少避免了数据库回滚但消息已经被消费的问题。更严格的生产方案可以引入 Outbox 表，在同一个事务里写业务表和消息表，再由独立任务扫描消息表投递 MQ。

### 2. 如果 MQ 发送失败怎么办？

当前项目是校招版简化实现，会在日志中暴露发送异常。生产上我会引入本地消息表，把待发送消息持久化，再由定时任务补偿发送，保证最终一致。

### 3. Redis 锁会不会失效？

Redis 锁设置了 TTL，避免应用宕机导致死锁。同时不能只依赖 Redis，所以数据库层给 `biz_id` 和结果表 `task_id` 都加了唯一索引，作为最终兜底。

### 4. 为什么结果表不直接放在任务表里？

任务主表主要关注状态流转和调度字段，结果表可能包含大文本、模型信息和耗时信息，单独拆表可以降低主表宽度，也方便后续扩展多版本结果或结果审计。

### 5. 任务优先级怎么体现？

当前在分页查询时按优先级排序，实际生产中可以进一步拆成不同优先级队列，或者使用延迟队列、优先级队列，让高优任务更快被消费者处理。

### 6. 如果消费者处理到一半宕机怎么办？

任务可能停留在 `PROCESSING`。我用定时任务扫描超时 `PROCESSING` 任务，把它标记为 `FAILED`，再由自动重试任务重新投递 MQ。

### 7. 缓存和数据库不一致怎么办？

项目采用更新数据库后删除缓存的策略。任务状态变化后主动删除详情缓存和结果缓存，下一次查询会回源数据库并重新写缓存。

### 8. 为什么不直接接入真实大模型？

因为这个项目是 Java 后端校招项目，重点不是模型效果，而是后端系统设计。Mock AI 服务保留了耗时、结果、token、模型名等业务字段，后续替换成真实模型调用也比较自然。

## 2 分钟项目介绍稿

我做过一个 AI 任务调度与结果管理平台，业务场景是企业内部用户提交文本摘要、风险识别、问答生成这类 AI 分析任务。因为 AI 任务耗时不稳定，所以我没有做成同步接口，而是用 Spring Boot 提供任务创建和查询接口，任务创建后先写入 MySQL，状态是 `PENDING`，然后在事务提交后投递 RabbitMQ，由消费者异步处理。

在工程设计上，我重点做了幂等、缓存、状态流转和失败补偿。创建任务时用 `bizId` 做业务幂等，Redis 锁防止并发重复提交，MySQL 唯一索引兜底。消费者处理任务时也会用 Redis 锁和任务状态判断避免重复消费，结果表也对 `task_id` 做唯一约束。

查询侧我用 Redis 缓存任务详情和任务结果，状态变化后主动删除缓存。失败处理上，任务执行异常会记录失败原因，支持手动重试；同时接入 XXL-Job 扫描超时任务和可重试失败任务，保证任务不会一直卡在处理中。这个项目主要体现的是 Java 后端里的异步任务、缓存、MQ、事务、幂等和调度能力。

## 5 分钟项目介绍稿

这个项目叫 AI 任务调度与结果管理平台，定位是一个企业内部的异步任务系统。用户可以提交摘要、风险识别、问答生成等 AI 分析任务，系统返回 `taskId`，后台异步执行，用户再通过查询接口查看任务状态和结果。

我设计这个项目时主要考虑了几个问题。第一，AI 任务耗时不稳定，如果同步处理会导致接口响应慢，所以我引入 RabbitMQ，把任务创建和任务执行解耦。创建接口只做参数校验、幂等检查、任务落库和消息投递，真正的 AI 处理由消费者完成。

第二是幂等问题。用户可能重复点击提交，也可能因为网络超时重试请求。我的做法是让调用方传 `bizId`，系统先查 Redis 的 `biz-task:{bizId}`，如果已经有任务就直接返回已有 `taskId`。如果没有，再获取 Redis 创建锁，防止并发创建。同时数据库对 `biz_id` 加唯一索引，即使 Redis 失效也不会重复插入。

第三是状态一致性。任务状态从 `PENDING` 到 `PROCESSING`，最后到 `SUCCESS` 或 `FAILED`。任务创建时，主表和日志表在一个事务里写入，事务提交后再发 RabbitMQ 消息，避免消息被消费但数据库没有任务记录。消费端处理时会先加 Redis 处理锁，再判断任务是否已经成功或已有结果，防止重复消费。

第四是缓存设计。任务详情和任务结果查询比较频繁，所以我用 Redis 做缓存，采用 Cache Aside 模式。查询时先读缓存，未命中查 MySQL 并回写缓存；任务状态变化或结果写入后删除缓存，减少读到旧数据的概率。

第五是失败补偿。任务执行异常会记录失败原因并标记为 `FAILED`。如果消费者宕机导致任务一直处于 `PROCESSING`，XXL-Job 会定时扫描超时任务并标记失败。失败任务可以手动重试，也可以由定时任务自动重试，但会受最大重试次数限制，避免无限重试。

这个项目里的 AI 服务是 Mock 的，因为项目重点不是算法，而是后端工程能力。真实接入大模型时，只需要替换 `MockAiModelService` 的实现，任务调度、状态管理、缓存和重试机制都可以复用。
